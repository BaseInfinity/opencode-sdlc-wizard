## Testing tiers (data-science-adapted pyramid)

ML testing isn't symmetric to web: model behavior is the dominant
risk, and "all unit tests pass" is meaningless if the model itself
silently degraded. The pyramid:

```
              ┌──────────────────┐
              │  Model evaluation │   end-to-end on holdout sets
              │   (held-out)      │   slow, definitive, gates release
              ├──────────────────┤
              │  Pipeline / data  │   data-loaders, feature transforms,
              │  integration      │   notebook reproducibility
              ├──────────────────┤
              │  Data validation  │   schema, range, drift, leakage
              ├──────────────────┤
              │  Unit              │   pure functions, math primitives
              └──────────────────┘
```

## What each layer covers

### Model evaluation

- Run the trained model against a held-out dataset that no train /
  val split has touched.
- Assert: accuracy / F1 / RMSE / domain-specific metric within a
  tolerance vs a baseline (last-released model).
- Slowest tier — usually only run on PR-to-main, not per-commit.
- Outcomes: ship, retrain, or escalate.

### Pipeline / data integration

- Reproduce a notebook end-to-end from raw data through model output.
- Catches: feature pipeline drift, train/serve skew, dependency
  pinning issues.
- Run notebooks under `papermill` or `jupyter nbconvert --execute`
  in CI so silent kernel-state cell-order bugs surface.

### Data validation

- Schema (column types, ranges, nullability) enforced at ingest.
- Statistical drift: alert when input distribution deviates from
  training data > threshold.
- Leakage: assert held-out IDs do not appear in train.
- Tools: Great Expectations, Pandera, custom checks.

### Unit

- Pure math / preprocessing functions: `normalize`, `tokenize`,
  `one-hot`, custom loss functions.
- No model loading, no I/O, no notebooks.
- Fast, runs every commit.

## Mocking rules

- **DO NOT mock the model.** A test that mocks the model output is
  testing the orchestration, not the ML system. Use a tiny real
  fixture model (a 2-layer net trained on 100 rows) for orchestration
  tests.
- **DO NOT mock the data loader.** Use a frozen test fixture
  (`tests/fixtures/<small>.parquet`) that exercises the same schema
  as production. Mocked loaders hide schema drift.
- **MAY mock external APIs** (feature stores, third-party labelers)
  if you have a contract test that runs nightly against the real
  endpoint.

## Notebook reproducibility

- Notebooks in `notebooks/` SHOULD run top-to-bottom in CI.
- Hidden state (cell run-order) is the usual silent bug — `Restart
  Kernel and Run All` should produce the same outputs.
- Use `nbstripout` pre-commit so committed notebooks have no outputs.

## Commands

```bash
# Unit tests
pytest tests/unit/                    # or your runner

# Data validation
python -m great_expectations checkpoint run <name>

# Pipeline / notebook reproducibility
papermill notebooks/<name>.ipynb /tmp/out.ipynb -p mode=test

# Model evaluation
python scripts/eval.py --model models/latest --holdout data/holdout.parquet
```

## Capability floor

Models that miss the metric tolerance against the held-out set don't
ship — that's by design, not a "test was flaky" excuse. If the holdout
set itself is stale (the world has moved), regenerate the holdout
before retraining; never relax the tolerance to make a release.
