## Testing tiers (CLI-adapted pyramid)

CLIs sit between web and firmware: the contract is the argv / stdin /
stdout / exit-code shape, and the tests assert that contract holds
across releases. End-to-end is cheap (just `./bin/foo`), so the
pyramid leans toward integration:

```
              ┌──────────────────┐
              │  CLI integration  │   spawn process, assert stdout +
              │  (process spawn)  │   stderr + exit code
              ├──────────────────┤
              │  Behavior         │   per-flag / per-subcommand,
              │  contract         │   uses CLI test harness
              ├──────────────────┤
              │       Unit         │   pure parsing / formatting
              └──────────────────┘
```

## What each layer covers

### CLI integration

- Actually invoke the binary as a subprocess. Capture stdout, stderr,
  exit code. Compare against expected.
- Tests live in `tests/integration/`. Use a fixture filesystem
  (tempdir) for any read/write commands.
- Catches: argv parsing bugs, stdout vs stderr leakage, exit code
  inversions, unhandled exceptions.

### Behavior contract

- One test per documented flag / subcommand. Asserts the documented
  behavior survives refactors.
- The CLI test harness can be the same one as integration, just with
  finer-grained assertions on individual outputs.

### Unit

- Pure parsing / formatting functions called from the CLI:
  argument parsers, output formatters, validators.
- No process spawning, no I/O.

## Mocking rules

- **DO NOT mock the OS / shell.** If your CLI reads from stdin, write
  to a real stdin in the test. If it spawns subcommands, let it
  actually spawn. The whole point of a CLI is the OS contract.
- **DO NOT mock the filesystem at the unit level.** Use a tempdir
  fixture (`tempfile.TemporaryDirectory()`, `mktemp -d`). Mocked
  filesystems lie about edge cases like permissions, symlinks, FS
  case-sensitivity.
- **MAY mock external services** (HTTP APIs the CLI calls) at the
  unit level. Have a contract test that hits the real service nightly.

## Behavior contract documentation

Every documented flag has a test. Drift between docs and behavior is
the most common CLI bug.

| Flag / Subcommand | Documented behavior | Integration test |
|-------------------|---------------------|------------------|
| `<--foo>` | `<expected behavior>` | `<test path>` |
| `<bar subcommand>` | `<expected behavior>` | `<test path>` |
| `--help` | prints usage to stdout, exit 0 | `<test path>` |
| `--version` | prints version to stdout, exit 0 | `<test path>` |
| invalid flag | prints usage to stderr, exit ≥ 2 | `<test path>` |

## Snapshot tests

CLIs benefit from snapshot tests of stdout for fixed inputs. Use the
test runner's snapshot feature (`pytest-snapshot`, `vitest`'s
`toMatchSnapshot`, etc.). Update snapshots deliberately — auto-update
in CI defeats the point.

## Commands

```bash
# Unit tests
<unit-test-command>            # e.g. pytest tests/unit/, vitest run unit

# Integration tests (process spawn)
<integration-test-command>     # e.g. pytest tests/integration/

# Smoke test (manual, fast sanity)
./bin/<your-cli> --help
./bin/<your-cli> --version
```

## Capability floor

A CLI's exit code is its API. Tests that ignore exit codes ("works
on my machine") miss the most common breakage class. Every test
asserts an exit code, even if it's just `assert exit == 0`.
