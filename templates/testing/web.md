# TESTING.md (Web / API — default)

Domain-specific testing template generated by `opencode-sdlc-wizard`'s
setup-wizard skill. Replace `<...>` placeholders with project-specific
values during setup. This is the default fallback when no other domain
signal dominates.

## Testing tiers (web-adapted testing diamond)

Web/API testing: integration is the load-bearing tier because most
real bugs live at the boundary between services. The diamond inverts
the classic pyramid because mocked unit tests give false confidence
when the actual integration breaks.

```
              ┌──────────────────┐
              │       E2E         │   browser / API user flows
              ├──────────────────┤
              │   Integration     │   real DB, real cache, real HTTP
              │   (load-bearing)  │   the truth-seeking tier
              ├──────────────────┤
              │       Unit         │   pure functions, formatters
              └──────────────────┘
```

Diamond percentages: roughly 20% E2E / 60% integration / 20% unit.

## What each layer covers

### E2E

- Drive the system through its public interface (HTTP, WebSocket,
  GraphQL, browser).
- Test user-flow contracts: "user signs up → confirms email → can
  log in → can post a thing." Each step a real network call.
- Fixtures: ephemeral test database, seeded in `beforeAll`.
- Tools: Playwright / Cypress for browser. `supertest` / `httpx`
  for API-only.
- Slowest layer; usually 5-20% of test time.

### Integration

- Hit the database. Hit the cache. Hit external services via
  contract tests.
- This is where most bugs live. SQL ordering, transaction boundaries,
  connection pool exhaustion, query plans on real-shaped data — none
  of this shows up in unit tests.
- Per service / route, write integration tests that assert the real
  HTTP behavior including auth, validation, and error paths.

### Unit

- Pure functions: validators, formatters, business-rule predicates.
- Fast, runs every save in dev.
- DO NOT inflate this tier to game a coverage metric — false security.

## Mocking rules

- **DO NOT mock the database.** Spin up a real one (sqlite for
  speed, postgres-in-docker for parity). Mocked DBs hide migration
  bugs and SQL dialect differences.
- **DO NOT mock the cache** unless the cache is genuinely irrelevant
  to the test. Real cache (`redis-mock` is OK for integration; real
  Redis for E2E).
- **MAY mock external HTTP APIs** but ONLY with a contract test that
  hits the real endpoint nightly. Mocked third-party APIs lie about
  rate-limits, timeouts, and breaking changes.

## Test types

| Type | Lives in | Speed | What it catches |
|------|----------|-------|-----------------|
| `<unit>` | `tests/unit/` or `*.test.ts` next to source | < 50ms each | logic / regex / pure transforms |
| `<integration>` | `tests/integration/` or `*.spec.ts` | ~ 100-500ms each | DB / cache / HTTP / auth |
| `<e2e>` | `tests/e2e/` or `e2e/` | seconds each | user flows |

## API contract tests

For every endpoint your service publishes, an integration test
covers:
1. Happy path with valid inputs
2. Validation: each invalid input shape returns the documented 4xx
3. Auth: unauthenticated, wrong role, expired token
4. Rate limit / pagination behavior

Drift between OpenAPI spec and integration test is the most common
API bug. CI should validate the spec → test mapping is exhaustive.

## Commands

```bash
# Unit tests
<unit-command>             # e.g. npm run test:unit, pytest tests/unit

# Integration tests (real DB)
<integration-command>      # e.g. npm run test:integration

# E2E (real browser / real network)
<e2e-command>              # e.g. npx playwright test, npx cypress run

# All
<all-command>              # e.g. npm test
```

## Capability floor

Don't ship if integration tests fail with "flaky network" — that's
the production network breaking, just on dev. Reproduce locally and
fix; don't retry in CI to make it green.
