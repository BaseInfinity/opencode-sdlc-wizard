## Testing tiers (firmware-adapted pyramid)

Firmware testing inverts the classic web pyramid because the hardware
is the truth. Unit-only coverage doesn't catch register-level or
timing bugs, and the cost of a bad release on real hardware is high.

```
              ┌──────────────────┐
              │  Hardware-in-Loop │   real device + test harness
              │      (HIL)        │   slow, expensive, definitive
              ├──────────────────┤
              │  Software-in-Loop │   simulator + emulator
              │      (SIL)        │   moderate speed, scriptable
              ├──────────────────┤
              │  Config validate  │   .cfg / device-tree / fuse-bit lint
              ├──────────────────┤
              │       Unit         │   pure-logic functions only
              └──────────────────┘
```

Layer percentages are project-dependent; HIL coverage is usually
target-area-driven (every shipping board, every shipping firmware
variant) rather than statement-driven.

## What each layer covers

### Hardware-in-Loop (HIL)

- Run firmware on the actual silicon via JTAG / SWD / serial.
- Assert real-world behavior: GPIO levels, timing windows, register
  state after a peripheral interrupt, current draw at idle.
- Test fixtures: bench-top harness (logic analyzer, oscilloscope,
  programmable load) wired to test runner.
- Pre-merge gates: usually a curated subset (smoke). Full HIL on
  release branch.

### Software-in-Loop (SIL)

- Run firmware (or its core modules) under a CPU emulator (QEMU
  for ARM, Renode, custom simulator).
- Tests that would be too slow / expensive / dangerous on real
  hardware: fault injection, fuzzing peripheral inputs, large
  parameter sweeps.
- Faster than HIL, slower than unit. Catches integration bugs that
  unit can't see.

### Config validation

- Lint device trees, fuse-bit configs, linker scripts, board variants.
- Cross-check that every supported board's config compiles and that
  build artifacts are sized within flash/RAM budgets.

### Unit

- Pure-logic functions only. No hardware access, no global state.
- Examples: protocol parsers, CRC, ring-buffer logic, state machines
  modeled as pure functions.
- Run on the host (x86) under a normal test framework. Fast.

## Mocking rules

- **DO NOT mock the hardware.** Mocked HIL is the worst-of-both:
  passes the test but doesn't prove the device works. If you can't
  HIL, mark the case `@hil-required` and run on the next bench cycle.
- **DO NOT mock peripherals.** Use the SIL emulator if you need to
  drive register state — emulators are imperfect but they're not lies.
- **MAY mock OS / RTOS primitives** (mutex, queue) only if your test
  isn't about timing or contention. Otherwise use the real RTOS in
  SIL.

## Capability floor

Don't gate releases on bugs found only on a board you don't ship. A
failed test on an unsupported variant is a capability result, not a
release blocker.
