## Invoking the workflow

For the full plan → TDD → self-review workflow on any non-trivial
change, invoke the SDLC skill:

```

```

The skill walks you through the steps below. Smaller changes can
follow this doc directly without invoking the skill — the skill is
just the structured version of these rules.

## SDLC baseline (every session)

1. **Plan before coding** — state confidence (HIGH / MEDIUM / LOW)
   before writing the first line. Confidence is about whether you
   understand the problem well enough to ship; it's not about
   estimating difficulty.
2. **TDD: write the failing test FIRST**, then implement until green.
   Don't write tests after the fact — they pass for the wrong
   reasons.
3. **All tests must pass before commit** — no exceptions, no
   `--no-verify`, no "I'll fix it in the next commit." Failing tests
   are a blocker, not a TODO.
4. **Self-review the diff** before presenting. Read every line. Look
   for: things you'd push back on if a colleague wrote them, magic
   numbers, copy-pasted code, fallback paths to legacy that should
   just be deleted.
5. **LOW confidence → ASK USER** before proceeding. The cost of one
   clarifying message is much less than the cost of a wrong
   implementation.
6. **Failed twice → STOP and ASK USER**. Don't spin.

## Workflow phases

### 1. Plan (research + outline)

- Read the relevant code paths. Don't guess at the interface.
- Outline the change as bullet points. Show it to the user before
  writing.
- State confidence. If LOW, ask.

### 2. Transition (update docs)

- Feature docs current before commit. If your change adds an
  endpoint, update OpenAPI / README. If it adds a flag, update
  `--help` output AND the docs.

### 3. Implementation (TDD)

- RED: write the failing test
- GREEN: write the minimal code to pass
- REFACTOR: clean up while still green

### 4. Self-review

- Read every modified file end-to-end before presenting
- Run the full test suite (`<test-command>`)
- Check git diff for: `console.log`, debug prints, commented-out
  code, TODOs introduced in this change

### 5. Cross-model review (high-stakes changes)

For changes that touch:
- Auth / billing / privileged data paths
- Migration scripts / data transforms
- Public API surfaces
- Release-critical infra

Run a cross-model review. Two paths:
- **Codex flow** (OpenAI gpt-5.5): `codex exec
  -c 'model_reasoning_effort="xhigh"' -s danger-full-access
  -o .reviews/latest-review.md "<recheck-prompt>" </dev/null`
- **OpenCode + OSS flow** (no Anthropic+OpenAI dependency): invoke
  `skill({ name: "cross-model-review" })` or run
  `bash .opencode/scripts/cross-model-review.sh
  --reviewer-provider togetherai --reviewer-model deepseek-ai/DeepSeek-V3`

CERTIFIED → ship. NOT CERTIFIED → fix loop, cap at 3 rounds total.

## Confidence levels (calibrated)

- **HIGH**: I've read the code, I understand the constraints, I know
  the tests, I can predict the diff. Proceed without asking.
- **MEDIUM**: I have a plan but there's a load-bearing assumption I
  haven't verified. State the assumption + plan, get an "OK" from
  the user, then proceed.
- **LOW**: I'm not sure of the right approach OR there are competing
  ones with material trade-offs. STOP and ask.

LOW != "this is hard." LOW means "I might be wrong about the goal."

## Cross-cutting rules

- Don't `--no-verify` to bypass hooks. If a hook fails, fix the
  underlying issue.
- Don't add fallbacks to legacy code paths. If something is
  deprecated, delete it.
- Don't add error handling for cases that can't happen. Trust
  internal callers; validate at system boundaries (user input,
  external APIs).
- Don't introduce abstractions before the second use case. Three
  similar lines beats a premature abstraction.
- Comments are for non-obvious WHY (a hidden constraint, a
  surprising invariant). Don't comment what well-named code already
  says.
